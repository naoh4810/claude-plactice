# APIキーなしで「AIが画面を操作するデモ動画」を作った話 — 提案資料に“動くもの”を足す一日

AI活用の提案をしても「で、実際どう動くの?」で止まってしまう——これは私が副業でAIコンサルをしていて一番よく当たる壁です。この記事は、APIキーの発行や新規契約なしで「AIが実際に画面を操作する様子」を録画し、提案資料とセットで渡すまでの実作業ログです。中小企業の担当者で、社内や取引先にAIの提案を通したい方に向けて書きます。

## なぜ「操作デモの録画」が必要だったのか

今回の相手は、ふるさと納税まわりの業務を扱う事業者様（以下、ロケトク様）です。課題として挙がっていたのは、返礼品の登録作業とSNS運用の負荷でした。

この手の話を資料だけで説明すると、だいたい次の反応になります。

- 「AIが代わりにやってくれる、というのは分かるけど、イメージが湧かない」
- 「うちの画面でも同じことができるの?」
- 「結局、人が全部チェックするなら楽にならないのでは?」

3つ目が特に重要です。**AIが「全自動でやる」と言うほど、現場は不安になります。** だから今回は「AIが操作している画面」と「人が承認する画面」の両方を見せる、という方針にしました。文章で100行書くより、30秒の録画のほうが早いからです。

## APIキーなしでやる、という制約をあえて受け入れる

提案段階でAPIキー（AIサービスを外部から呼び出すための認証用の文字列。通常は従量課金と結びつきます）を発行してもらうのは、実はハードルが高い作業です。

- 費用の稟議が必要になる
- 情報システム部門の承認が必要になる
- 「まだやるか決めてないのに、なぜ契約するのか」と当然なる

つまり、**APIキーを求めた時点で提案が1〜2週間止まる**わけです。そこで今回は、API連携を一切使わず、Claude Code（ターミナルで動くAIコーディング支援ツール）に画面そのものを見せて操作させる形、いわゆる Computer use（AIが画面を認識して、マウスやキーボードの操作を代行する使い方）でデモを組みました。

この構成のメリットは明確です。

- 既存の業務システムに手を入れない（改修ゼロ）
- 先方のシステム管理者の承認を待たずに検証できる
- 「今の画面のまま使える」ことがそのまま伝わる

逆に、速度や安定性はAPI連携に劣ります。ここは正直に伝える前提で進めました。提案資料にも「本番運用ではAPI連携に切り替える選択肢がある」と併記しています。

## 録画は「通常版」と「リニューアル版」の2本立てにした

返礼品登録の操作デモを録画したのですが、ここで1本では足りませんでした。

理由は、先方が画面のリニューアルを予定していたからです。現行画面だけで撮ると「新画面になったら使えないのでは?」という質問が必ず出ます。かといって新画面だけだと「今日から試せない」話になってしまいます。

そこで、

1. **通常版**（現行の登録画面で、AIが入力・登録していく様子）
2. **リニューアル版**（新しい画面でも同じ流れが成立する様子）

の2本を撮りました。狙いは「画面が変わってもやり方は変わらない」という一点を、口頭ではなく映像で示すことです。Computer useは画面を見て判断する方式なので、レイアウトが変わっても同じ指示で動けるケースがあります。それを言葉ではなく、2本並べて見せたほうが早いという判断でした。

## SNS運用は「調査 → 3案 → 実装」まで持っていく

提案資料と並行して、SNS運用の調査を行い、3つの案を作りました。それぞれスライドの文字ではなく、動く形（デモ）まで作っています。

**案1:投稿案の承認画面**
AIが投稿文の候補を生成し、人が画面上で「承認/却下/修正」を選ぶ形。全自動にしないのがポイントで、「AIに任せきりになるのが怖い」という不安に対する直接の回答になります。

**案2:加盟店投稿キット**
加盟店さんが自分で投稿できるよう、素材とテンプレートをセットにして渡す形。運用の負荷を本部に集中させない設計です。

**案3:観光サイト掲載代行**
返礼品や地域の情報を、観光系サイト向けの掲載フォーマットに整えて出す形。既存の情報資産を別の出口に流し直す発想です。

3案に分けたのは、**「どれか1つを選んでください」ではなく「どこから始めますか」に話を変えるため**です。1案だけ持っていくと、採否のイエス・ノーになります。3案あると、優先順位の相談になります。この差は提案の現場では大きいです。

## つまずいた点と解決

**1. 「全自動」に見せようとして、かえって不安を与えかけた**

最初の構想では、AIが投稿まで一気にやる流れを想定していました。しかし現場目線で考え直すと、自社名で出る投稿を誰のチェックもなく出すのは、普通は怖いです。製造業でも、自動化した工程ほど「異常を検知する人の目」をどこに置くかが設計の肝になります。同じです。そこで案1を「承認画面」に変えました。AIは案を出すところまで、最終判断は人、という線を明示したことで、デモの意味がはっきりしました。

**2. デモ録画が「現行画面専用」に見えてしまう問題**

これが前述の2本立てにした理由です。1本撮った時点で見返し、「これ、画面変わったら終わりだと思われるな」と気づいて、リニューアル版を追加撮影しました。デモは撮ってから第三者目線で一度見ることをおすすめします。自分では伝わっているつもりの部分が、だいたい一番伝わっていません。

**3. API前提で考えると提案が前に進まない**

これは最初の設計ミスでした。技術的に筋が良い方法（API連携）と、提案が通りやすい方法（画面操作）は別物です。検証フェーズでは後者を選ぶ、と割り切ってから作業が一気に進みました。

## 明日から使えるチェックリスト

AI活用の提案を社内外に持っていく人向けに、今回の実作業から抽出したものです。

- [ ] 提案の中に「30秒〜1分の操作録画」を1本入れる（スライドだけにしない）
- [ ] 検証フェーズでは**新規契約・APIキー発行を必要としない構成**を選ぶ
- [ ] AIが「全部やる」デモではなく、**人が承認する画面**を必ず映す
- [ ] 画面リニューアルや仕様変更の予定を事前に聞き、**現行版と新版の2パターン**を用意する
- [ ] 提案は1案ではなく**3案**にして、「やるか否か」ではなく「どこから」の会話にする
- [ ] 録画したら必ず一度、相手の立場で見返す（「これ、うちでも使えるの?」と自問する）
- [ ] 画面操作方式の弱点（速度・安定性）は隠さず資料に明記し、将来のAPI移行も併記する

## この学びが解決する実務の課題

一番大きいのは、**AI導入の提案が「検討します」で止まる問題**です。止まる原因の多くは、技術ではなく想像力のギャップにあります。動いている画面を30秒見せるだけで、そのギャップは埋まります。しかも今回の方法なら、相手側のシステムに一切手を入れず、契約も発生しません。

## まとめ

- APIキーなしの画面操作デモなら、契約・改修ゼロで「動くもの」を見せられます。
- 全自動ではなく「人が承認する画面」を見せたほうが、現場の納得感は上がります。
- 提案は3案に分け、採否の判断ではなく優先順位の相談に持ち込むのが有効でした。
