# クラウド版Difyの「アプリ10個まで」に詰まったので、Dockerでセルフホストに移行した話

クラウド版Dify（ノーコードでAIアプリを作れるツール）の無料プランは、作れるアプリが10個まで。そこに到達してしまったので、自分のPC上で動くセルフホスト版へ移行しました。Docker未経験の状態から環境構築し、クラウド版で作ったアプリをそのまま移すところまでを、実際の手順ベースで書きます。

## きっかけは「アプリ数の上限」という地味な壁

Difyでアプリを作っていると、検証用・本番用・顧客向けデモ用とファイルが増えます。研修や試作で使っていると、10個はあっという間です。

上限に当たったときの選択肢は3つでした。

1. 有料プランに切り替える（月額コストが発生する）
2. 古いアプリを消しながら使い回す（過去の資産が消える）
3. セルフホスト版に移行する（自分のマシンで動かす）

今回選んだのは3番目です。理由は3つあって、**アプリ数が無制限になること**、**入力したデータが社外のサーバーに出ないこと**、**月額費用がゼロになること**。特に2つ目は、製造業の現場で図面情報や工程データを扱う立場からすると大きい。「このデータ、外部サービスに入れていいんでしたっけ」という社内確認を毎回やらずに済むのは、実務では想像以上に効きます。

なお、ここで言う「セルフホスト」とは、クラウド事業者のサーバーではなく、自分の手元のPCやサーバーにソフトを入れて動かすことです。

## 実際にやった手順

### 1. Docker Desktopを入れる

Dify本体の前に、まずDockerが必要です。Dockerは、アプリの動作に必要な環境をひとまとめにした「箱（コンテナ）」を動かす仕組み。データベースやWebサーバーを個別にインストールせずに済むのが利点です。

やることは公式サイトからDocker Desktopをダウンロードしてインストールするだけ。ただし初回は、OSの設定変更や再起動が挟まります。ここは焦らず、インストーラの指示通りに進めます。

インストール後、ターミナル（Windowsならコマンドプロンプト／PowerShell）で以下を実行し、バージョンが表示されればOKです。

```
docker --version
docker compose version
```

### 2. Difyを取得して起動する

DifyのリポジトリをGitHubから取得し、`docker`フォルダに移動して起動します。

1. `git clone` でDifyのリポジトリを取得する（Gitが無ければZIPダウンロードでも可）
2. `cd dify/docker` でdockerフォルダへ移動
3. `cp .env.example .env` で設定ファイルの雛形をコピー
4. `docker compose up -d` で起動

`up -d`を打つと、Difyを構成する複数のコンテナが一斉にダウンロード・起動されます。**ここが初回で一番時間がかかるところ**で、画面には見慣れないログが延々と流れます。初めてだと「何かおかしいのでは」と不安になりますが、ネットワーク経由でイメージを取得しているだけなので、止めずに待つのが正解です。

起動後、ブラウザで `http://localhost` にアクセスすると、クラウド版と同じ見た目の管理画面が出ます。初回はここで管理者アカウントを作成します。

### 3. モデルプロバイダー（APIキー）をつなぐ

セルフホスト版には、当然ながらAIモデルは付いてきません。**自分でAPIキーを用意して接続する**必要があります。今回はAnthropicのAPIキーを使いました。

1. 右上のアカウントメニューから「設定」→「モデルプロバイダー」を開く
2. Anthropicを選び、APIキーを貼り付けて保存
3. 一覧に有効なモデルが表示されるのを確認

ここを飛ばすと、アプリを開いても「モデルが選べない」状態になります。アプリを作る前に必ず済ませておくのが順番です。

### 4. クラウド版のアプリをDSLで移送する

ここが今回の本命です。Difyには、アプリの設定一式をYAML形式のファイル（DSL）として書き出す機能があります。プロンプト、ワークフローの構成、変数の設定などがテキストで丸ごと保存されるイメージです。

1. クラウド版Difyで、移したいアプリを開く
2. アプリ名の横のメニューから「DSLファイルをエクスポート」を選び、`.yml`ファイルを保存
3. セルフホスト版のトップ画面で「アプリを作成」→「DSLファイルをインポート」
4. 保存した`.yml`ファイルを指定してインポート
5. 開いて動作確認する

今回は、クラウド版で作っていた旅行プラン作成アプリをこの手順で移し、ローカル環境で同じように動くところまで確認できました。手作業でプロンプトをコピペし直す必要はありません。

## つまずいた点と解決

今回、手が止まりかけたのは次の3か所でした。

**1. 起動に時間がかかり「失敗した」と勘違いしかける**
Difyは1つのアプリに見えて、内部はAPI・ワーカー・データベース・ベクトルDBなど複数のコンテナの集合体です。`docker compose up -d`を打った直後はそれらを順番に取得・起動していくため、ログの量も待ち時間も多くなります。対処法は単純で、**Docker Desktopの画面でコンテナが緑（running）になっているかを目で確認する**こと。ターミナルのログだけ見ていると不安になりますが、GUIで状態を見れば「動いているのか、落ちているのか」が一目で分かります。

**2. アプリを開いてもモデルが選べない**
クラウド版の感覚のまま移行すると、ここで引っかかります。セルフホスト版は「器」だけなので、APIキーの登録は自分でやる作業です。先にモデルプロバイダー設定を済ませてからアプリをインポートする、という順番にすると迷いません。

**3. そもそも「移行＝作り直し」だと思い込んでいた**
最初はアプリを一から作り直すつもりでいました。DSLエクスポート／インポートの存在を知ってからは、移行作業が数クリックで終わります。**上限に当たったら消す前に、まずDSLで書き出しておく**。これだけで過去の資産は守れます。

## この環境が解決する実務の課題

中小企業の現場に当てはめると、効いてくるのは次の3点です。

- **試作をためらわなくなる**：アプリ数の上限がないので、「とりあえず作って試す」が無料でできる。業務改善は試行回数がものを言うので、ここが一番大きい。
- **社外にデータを出さずに検証できる**：ローカル環境で動くため、社内文書や取引先名を含む試作でも、情報管理の議論で止まりにくい（※外部のAPIを呼ぶ部分は別途モデル提供元に送信される点は要注意）。
- **コストが従量課金だけになる**：月額のサブスクではなく、実際に使ったAPI分だけ。小さく始めたい会社には合っています。

一方で、PCを止めればアプリも止まる、バックアップは自己責任、という運用上の手間は増えます。社内共有する段階では、サーバーに置く構成を別途考える必要があります。

## まとめ

クラウド版Difyのアプリ数上限は、有料化ではなくセルフホストでも解けます。
DSLのエクスポート／インポートを使えば、作ったアプリは作り直さずそのまま移せます。
Docker未経験でも、手順は「入れる・起動する・APIキーを入れる・インポートする」の4つだけです。
