# AIにPC操作をさせる「Computer use」は誰に提案すべきか——営業シートでの仕分けと、ふるさと納税の返礼品登録デモ試作ログ

AIがブラウザやアプリを人間の代わりにクリック・入力してくれる「Computer use」。便利そうに見えますが、すべての業務に向いているわけではありません。この記事は、見込み客ごとに向き不向きを仕分けし、実際にデモを試作したところまでの実録です。これからAI導入を検討する中小企業の方、AI提案をする立場の方に向けて書いています。

## Computer useとは何か、ざっくり言うと

Computer use（コンピュータ・ユース）は、AIがパソコンの画面を見て、マウスのクリックやキーボード入力を自分で行う機能です。従来のAI活用が「文章を書く・要約する」だったのに対し、こちらは「画面を操作する」側にあたります。

現場の感覚で言い換えると、**新人に「この画面のここを押して、ここに品名を入れて、最後に登録ボタン」と教えるのと同じことを、AIに任せる**イメージです。人間が見て判断しながら進める作業を、そのまま肩代わりできるのが特徴です。

重要なのは、これがRPA（決まった操作を自動で繰り返すツール）とは少し性質が違う点です。RPAは画面のボタン位置がずれると止まりますが、Computer useは画面を「見て」判断するため、多少レイアウトが違っても進められる可能性があります。逆に言えば、毎回まったく同じ動きをする保証はありません。この違いが、後述する向き不向きの判断に効いてきます。

## 営業シートを開いて、見込み客ごとに「合う／合わない」を仕分けた

この日やったことの一つ目は、手元の営業シート（見込み客リスト）を上から見ながら、それぞれの業務にComputer useが合うかどうかを整理する作業でした。

正直に言うと、新しい機能を知った直後は「全部に提案できるのでは」と思ってしまいます。実際、私も最初はそう考えました。しかし一件ずつ具体的な業務に当てはめていくと、明らかに向かないものが出てきます。

仕分けのときに私が使った判断軸は、次のようなものです。

- **APIや公式連携があるか** — システム同士をつなぐ正式な窓口（API）が用意されているなら、画面操作より確実で速い。わざわざAIに画面を触らせる理由がない
- **操作の途中に「人間の判断」が挟まるか** — 単純な転記だけなら自動化しやすい。「この内容でよければ承認」が入るなら、どこで人が止めるかを設計する必要がある
- **間違ったときの被害が戻せるか** — 社内ツールへの下書き登録なら修正できる。対外的な送信や決済が絡むと話が変わる
- **画面が特殊すぎないか** — 古い業務システムで、独自の操作体系になっている場合は検証コストが跳ね上がる

この軸で見ていくと、「合う」に残るのは意外と絞られます。そして残ったものは、**提案の説得力が格段に上がります**。「できるかもしれません」ではなく「ここは合います、ここは合いません」と言い切れるからです。

## ロケトク向け：返礼品を2つのポータルに登録するデモを試作

仕分けの結果として、具体的なデモ作成に進んだのが、ふるさと納税関連のサービスを手がける亀山さん（ロケトク）向けの案件です。

### 想定した業務

ふるさと納税の返礼品は、複数のポータルサイトに掲載されます。事業者側から見ると、**同じ商品情報を、サイトごとに違う入力画面へ、何度も登録する**という構造になります。品名、説明文、価格、画像、配送区分——内容は同じなのに、フォームの項目名や並び順はサイトごとに異なる。典型的な「人間がやると消耗するが、頭はほとんど使っていない」作業です。

ここはComputer useの適性が高い領域だと判断しました。理由は、

- 入力する情報の元データ（商品マスタ）は一つにまとまっている
- サイトごとの差異は「画面の見た目」であって、業務の中身ではない
- 登録後に人が目視確認する工程を挟める

### デモの作り方

デモでは、**架空のふるさと納税ポータルを2つ用意**しました。本番サイトをいきなりAIに触らせるわけにはいきませんし、実在サービスで試すのは相手にも迷惑がかかります。

ポイントは「2つ」にしたことです。1つだけだと「その画面専用に作り込んだのでは」と見えてしまう。項目名も並び順も違う2サイトに、同じ商品情報を登録してみせることで、「サイトが増えても同じ仕組みでいける」という話が伝わります。提案デモは、技術の性能よりも**拡張性が見える形**にするほうが響く、というのが現場で得た実感です。

## つまずいた点と解決

### つまずき1：全員に提案したくなってしまう

最初のつまずきは技術ではなく、自分の頭の中でした。新機能を知ると、営業シートの全件に当てはめたくなります。

**解決策は、「合わない理由」を先に書き出すルールにしたこと。** 一件ごとに「この案件でComputer useを使わないとしたら、理由は何か」を先に考える。APIがある、判断が多すぎる、失敗の影響が大きい——理由が出てくる案件は、そこで止めます。結果として提案リストは短くなりましたが、残ったものは自信を持って持っていけます。

### つまずき2：デモを作ったが、まだ実際には動かせていない

正直に書きます。この日の時点で、**デモの設計と架空サイトの準備までは終わりましたが、実際にClaudeを動かす実行はできていません**。APIキー（AIを外部から呼び出すための認証キー）の設定がまだだったためです。

ここで学んだのは、作業の順番です。「先にAPIキーの準備を済ませてから、作り込みに入るべきだった」という単純な反省なのですが、新しいことを試すときほど、面白い部分（デモのシナリオ作り）から手を付けてしまいます。

**解決策として、次回からは「環境の準備」を着手前のチェック項目に固定しました。** APIキーの発行、課金設定、動作確認の一往復。この3つが終わるまでは中身を作らない。製造現場で言う段取り八分と同じ話で、頭では分かっていても新しい技術だと抜けるものだと痛感しました。

## 明日から使えるチェックリスト

Computer useを自社業務や顧客提案に当てはめるとき、そのまま使える形で整理しておきます。

**ステップ1：候補業務の洗い出し**

1. 「同じ情報を、複数の場所に入力している」作業を探す
2. その作業の1回あたりの所要時間と、月間の回数をメモする

**ステップ2：向き不向きの仕分け（4つの質問）**

- [ ] その連携にAPIや公式の一括登録機能はないか？（あるならそちらが先）
- [ ] 作業の途中に人間の判断・承認が入るか？入るなら、どこで止めるか決めたか
- [ ] AIが間違えた場合、あとから取り消せるか？
- [ ] 操作対象の画面は、極端に特殊な作りになっていないか？

**ステップ3：デモを作るなら**

- [ ] 本番環境ではなく、**検証用の画面を自作**する
- [ ] 検証用の画面は**2種類以上**用意し、レイアウトをあえて変える
- [ ] 元データ（商品マスタなど）は1つにまとめておく

**ステップ4：着手前の段取り（ここを飛ばさない）**

- [ ] APIキーを発行済みか
- [ ] 課金・利用上限の設定を確認したか
- [ ] 最小構成で1回動かし、動作を確認したか

## まとめ

Computer useは万能ではなく、「APIがない・画面操作が繰り返される・やり直しがきく」業務で光ります。提案デモは、あえて異なる画面を2つ用意すると拡張性が伝わります。そして新技術ほど、APIキーなどの段取りを先に済ませる——この順番を守れば、面白い部分に時間を使えます。
