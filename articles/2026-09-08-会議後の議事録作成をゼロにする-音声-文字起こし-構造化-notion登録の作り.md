# 会議後の議事録作成をゼロにする：音声 →文字起こし →構造化 →Notion登録の作り方

会議が終わったあと、録音を聞き返しながら30分〜1時間かけて議事録を書く。この作業を「工程として分解して自動化する」と、ほぼゼロにできます。この記事では、製造業の現場で働きながらAI研修をしている立場から、実際に組んだ議事録の導線と、そこでつまずいた点を共有します。AIツールを「使ってみた」の次に進みたい方向けです。

## なぜ「要約させる」ではなく「導線を作る」のか

最初は素直に、文字起こしを生成AIに貼り付けて「議事録にまとめて」と頼んでいました。出てくるものは読めるのですが、毎回フォーマットが違い、決定事項とただの雑談が同じ重みで並び、結局手で直すことになります。手直しに20分かかるなら、自動化した意味が半分以下になってしまいます。

そこで考え方を変えました。議事録作成を「AIに丸投げする1つの作業」ではなく、**4つの独立した工程**として分解する。製造ラインと同じで、工程を分けると、どこが不良の原因かが見えるようになります。

1. **録音**（音声ファイルを決まった場所に置く）
2. **文字起こし**（音声 → テキスト）
3. **構造化**（テキスト → 決まった項目に整理）
4. **登録**（整理済みデータ → Notionのデータベース）

工程を分けた効果は大きく、「議事録の質が悪い」という曖昧な悩みが、「文字起こしの精度の問題」「構造化プロンプトの問題」のどちらかに切り分けられるようになりました。

## 工程2：文字起こしは「後で直せる前提」で割り切る

文字起こしは、音声認識のモデル（音声をテキストに変換するAI）を使います。クラウドのAPIでもローカルで動かすモデルでも構いませんが、選ぶときの基準は次の3点でした。

- 会議1本ぶんの長さ（数十分〜1時間超）をそのまま投げられるか
- 社内の音声を外部に出してよいか（社内規程の確認が先）
- テキストをファイルとして受け取れるか（画面に表示されるだけだと次の工程につながらない）

ここで大事なのは、**文字起こしの精度を100%にしようとしないこと**です。専門用語や社内の略語は必ず誤変換されます。それを次の工程で吸収する設計にしたほうが、はるかに早く動くものができます。

## 工程3：構造化は「出力の型」を先に決める

ここが導線全体の心臓部です。ポイントは、AIに文章を書かせるのではなく、**決まった項目を埋めさせる**ことです。

私が使っている項目は次の通りです。

- 会議名 / 日付 / 参加者
- 決定事項（箇条書き）
- ToDo（誰が・何を・いつまでに）
- 保留・持ち越し事項
- 議論の要点（背景がわかる程度の分量）

プロンプトは、おおよそこういう形にしています。

```
あなたは議事録作成の担当者です。以下の文字起こしから、
指定のJSON形式のみを出力してください。

# ルール
- 文字起こしに書かれていない内容を補完しない
- 発言者が特定できない場合は "不明" と記載する
- 決定していないことを決定事項に含めない
- 社内用語が誤変換されている可能性がある。文脈から明らかな
  誤変換は修正し、修正した語は notes に列挙する

# 出力形式
{
  "title": "", "date": "", "attendees": [],
  "decisions": [], 
  "todos": [{"owner":"", "task":"", "due":""}],
  "pending": [], "summary": "", "notes": []
}

# 文字起こし
（ここに貼る）
```

「書かれていない内容を補完しない」という一文がとても効きます。これを入れる前は、AIが議論の流れから“ありそうな結論”を勝手に作ることがありました。議事録でこれが起きると、後から事実確認ができない厄介な資料になります。

出力をJSON（プログラムが読み取れる形式のデータ）にしておくと、次の登録工程がそのまま繋がります。人が読む文章ではなく、機械が読むデータとして受け取るのがコツです。

## 工程4：Notionは「データベースのプロパティ設計」が先

Notion側では、議事録データベースを先に作り、プロパティ（列）を工程3のJSONの項目と1対1で対応させます。

- タイトル … title
- 日付（Date型）… date
- 参加者（Multi-select または Text）… attendees
- 決定事項・ToDo・要点 … ページ本文のブロックとして書き込む

NotionのAPIを使えば、この登録は自動化できます。ここまで繋がると、「録音ファイルを置く → 数分後にNotionに議事録ページができている」という状態になり、会議後の作業が“内容の確認と微修正”だけになります。

## つまずいた点と解決

**1. 長い音声を一度に処理できない**
1時間の会議の文字起こしをそのまま生成AIに投げると、扱える文字数の上限に当たります。解決策は、文字起こしを時間で分割し、まず区間ごとに要点を抽出し、その要点をまとめて最終構造化にかける二段構えにすることでした。工程を分けておいたおかげで、ここだけ差し替えれば済みました。

**2. 誰の発言かわからない**
話者の区別がつかないと、ToDoの担当者が埋まりません。完璧な話者分離を狙うより、**会議の冒頭で参加者名を一人ずつ声に出して録音する**という運用でかなり改善しました。ツールで解決しようとして詰まったら、運用側を1つ変えるほうが早いことがあります。

**3. Notion登録でエラーが出続けた**
原因は2つで、日付プロパティに「来週」など日付でない文字列が入っていたこと、そして長文をひとつのブロックに入れようとしたこと（リッチテキストは1つあたり2000文字の上限があります）。前者はプロンプト側で「日付が特定できない場合は空にする」と指定し、後者は本文を段落ごとに分割して送るようにして解決しました。

**4. 要約が抽象的で使えない**
「〜について議論した」で終わる要約は、読み返す価値がありません。項目を「決定事項」「保留」「ToDo」に分け、それぞれ**決まっていないことを書かせない**と明示したところ、実務で参照できる粒度になりました。

## 明日から使えるチェックリスト

1. まず1回の会議で、録音 → 文字起こしだけを手動でやってみる（自動化はまだしない）
2. 出てきた文字起こしを、自分の会社の議事録フォーマットに手で整理する
3. その整理作業を観察し、必要な項目を5〜7個に絞って書き出す
4. その項目をJSONの型としてプロンプトに埋め込む
5. 「書かれていないことを補完しない」「不明は不明と書く」をルールに入れる
6. Notionのデータベースを作り、プロパティ名をJSONの項目名と揃える
7. 録音を外部サービスに送ってよいか、社内の規程を確認する（ここは最初にやっても良い）
8. 3回動かして、手直しが必要だった箇所だけプロンプトを直す

## この導線が解決する実務の課題

効くのは「議事録作成の時間短縮」だけではありません。フォーマットが固定されるので、**人によって議事録の粒度が変わる問題**がなくなります。ToDoが必ず「誰が・何を・いつまでに」で残るため、次の会議で「あれ、これ誰の担当でしたっけ」が減ります。決定事項が検索できる場所に溜まっていくことも、地味ですが後から効いてきます。

## まとめ

議事録は「AIに丸投げする1作業」ではなく、録音・文字起こし・構造化・登録の4工程に分けると自動化できます。
鍵は、出力の型を先に決めて、書かれていないことを補完させないこと。
まずは1回、手作業で全工程を通してみるのが最短ルートです。
