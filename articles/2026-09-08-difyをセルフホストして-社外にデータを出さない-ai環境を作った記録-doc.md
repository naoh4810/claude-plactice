# Difyをセルフホストして「社外にデータを出さない」AI環境を作った記録（Docker Compose・DSL移送・月額ゼロ）

「AIは使いたいが、図面や見積、顧客名が入ったデータをクラウドに送るのは避けたい」——製造業の現場でよく聞く声です。この記事では、AIアプリ開発ツール「Dify」を自社サーバーにセルフホストし、クラウド版で作ったアプリを移送して月額ゼロで運用するまでの実作業と、その途中でつまずいた点を記録します。

## なぜセルフホストなのか（現場でぶつかった壁）

Difyは、ChatGPTのような対話AIや社内文書を検索するAI（RAG）を、コードをほとんど書かずに組み立てられるツールです。クラウド版（dify.ai）なら会員登録して数分で使い始められます。実際、最初のプロトタイプはクラウド版で作りました。

ただ、社内で展開しようとすると必ず同じ質問が出ます。

- 「そのデータ、どこのサーバーに保存されるんですか」
- 「取引先との秘密保持契約に抵触しませんか」
- 「無料枠を超えたら誰が払うんですか」

3つ目は地味に効きます。クラウド版には利用回数の制限があり、社内で10人が使い始めた途端に足りなくなります。かといって「まだ効果が分からないもの」に月額課金の稟議を通すのは、中小企業ではかなり大変です。

セルフホスト（自分たちのサーバーにソフトを設置して動かすこと）にすると、この3つが同時に解決します。データは自社のサーバー内、Dify本体はオープンソースなので利用料ゼロ、あとは動かすサーバー代だけ。社内の余っているPCやNASの上でも動きます。

## Docker Composeでの構築手順

Difyは公式にDocker Compose（複数のソフトをまとめて起動する仕組み）用の設定が用意されているので、Dockerさえ入っていれば手順自体は短いです。

1. サーバーにDockerとDocker Composeをインストールする（Ubuntu系なら公式のインストールスクリプトが手っ取り早いです）
2. Difyのリポジトリを取得する：`git clone https://github.com/langgenius/dify.git`
3. `cd dify/docker` に移動する
4. `cp .env.example .env` で環境変数ファイルを作る
5. `.env` を開き、最低限 `SECRET_KEY` を自前の値に変更する（`openssl rand -base64 42` で生成した文字列を貼る）
6. `docker compose up -d` で起動する
7. ブラウザで `http://サーバーのIP` にアクセスし、最初に管理者アカウントを作る

ここまでで、Difyの管理画面が自社サーバー上で動いている状態になります。あとは管理画面の「設定 → モデルプロバイダー」でOpenAIやAnthropic、あるいはローカルで動かすモデル（Ollamaなど）のAPIキーを登録すれば、アプリを作り始められます。

注意しておきたいのは、**セルフホストにしてもクラウドのAPIを呼べばデータはそこに出る**という点です。「データを社外に出さない」を完全に満たすなら、Ollamaなどでローカルモデルを動かす必要があります。私の場合は用途を切り分けました。

- 社外に出しても問題ない一般的な文章生成 → クラウドAPI（速くて賢い）
- 図面情報・顧客名を含む処理 → ローカルモデル

この線引きを最初に紙に書いて社内で合意しておくと、後の説明がとても楽になります。

## クラウド版からのDSL移送

セルフホストで一から作り直す必要はありません。Difyにはアプリの構成をYAML形式（DSL）で書き出す機能があります。

1. クラウド版でアプリを開き、右上のメニューから「DSLをエクスポート」を選ぶ
2. `.yml` ファイルがダウンロードされる
3. セルフホスト版のDifyで「アプリを作成 → DSLファイルをインポート」を選び、そのファイルをアップロードする

これでプロンプト、ワークフローのノード構成、変数定義がそのまま移ります。数時間かけて調整したワークフローが数十秒で移るので、この機能を知っているかどうかで移行コストがまったく変わります。

ただし、**移るのは「設計図」だけで「中身」は移りません**。具体的には次のものは手作業です。

- ナレッジ（RAG用にアップロードした文書）→ セルフホスト側で再アップロード
- APIキー → セルフホスト側で再登録
- 会話ログ → 移らない

## つまずいた点と解決

### 1. 起動はしたが画面が真っ白／502が出る

`docker compose up -d` の直後にアクセスすると、まだ内部の初期化（データベースのマイグレーション）が終わっておらず、エラー画面になります。焦って再起動を繰り返すと余計こじれます。

**解決**：`docker compose logs -f` でログを流し見して、初期化が終わるのを1〜2分待つ。ログが落ち着いてからアクセスすると普通に開きます。「起動コマンドが通った＝使える」ではない、というのが最初の学びでした。

### 2. メモリ不足でコンテナが落ちる

Difyは単体のアプリではなく、APIサーバー、ワーカー、PostgreSQL、Redis、ベクトルDB（Weaviate）などが同時に動きます。手元の非力なマシンで試したとき、コンテナが勝手に停止する現象に悩まされました。

**解決**：メモリを増やす。目安として最低4GB、実用なら8GBは見ておくべきでした。ローカルモデルまで同居させるなら、さらに上が必要です。「Dockerで動くから軽い」は誤解でした。

### 3. ポート80がすでに使われていた

社内サーバーに別のWebサービスが入っていて、起動時にポート競合でエラーになりました。

**解決**：`.env` の `EXPOSE_NGINX_PORT` を `8080` などに変更して `docker compose down` → `up -d` で解決。アクセス先も `http://サーバーIP:8080` に変わります。

### 4. DSLをインポートしたのにアプリが動かない

移送したワークフローを実行すると、モデル未設定のエラーで止まりました。DSLにはAPIキーが含まれないので当然なのですが、「移った」と思い込んでいたので原因特定に時間を使いました。

**解決**：移送後は必ず「モデルプロバイダーの登録 → ナレッジの再アップロード → ナレッジを参照するノードで参照先を再選択」の3点をチェックする、という手順書を自分用に作りました。ナレッジの参照先はIDで紐付いているため、再アップロードしただけでは繋がらず、ノード側で選び直す必要があります。ここが一番の落とし穴でした。

## 明日から使えるチェックリスト

**構築前**
- [ ] メモリ8GB以上のマシン（または VPS）を確保した
- [ ] 「社外に出してよいデータ／出せないデータ」の線引きを紙に書き、関係者と合意した
- [ ] 社内LANからのみアクセスさせるのか、外部公開するのかを決めた

**構築**
- [ ] `.env` の `SECRET_KEY` を自前の値に変更した
- [ ] ポート競合がある場合は `EXPOSE_NGINX_PORT` を変更した
- [ ] `docker compose logs -f` で初期化完了を待ってからアクセスした

**クラウド版からの移送**
- [ ] 各アプリのDSLをエクスポートした
- [ ] セルフホスト側でインポートした
- [ ] モデルプロバイダー（APIキー）を再登録した
- [ ] ナレッジ文書を再アップロードした
- [ ] ナレッジ参照ノードで参照先を選び直した
- [ ] 移送前と同じ入力を投げて、同じ挙動になるか比較した

**運用**
- [ ] `docker/volumes` 配下のバックアップ方法を決めた
- [ ] Difyのバージョンアップ手順（`git pull` → `docker compose up -d`）を試した

## まとめ

Difyのセルフホストは、Dockerが動く環境と8GB程度のメモリがあれば半日で立ち上がります。クラウド版で作ったアプリはDSLで移送できますが、移るのは設計図だけで、モデル設定とナレッジは手作業の再設定が必要です。「データを社外に出さない」を本当に満たすには、セルフホストに加えてローカルモデルの利用まで踏み込む必要がある——ここを最初に社内で線引きしておくのが、いちばんの近道でした。
