# Tallyフォーム→Make→メール通知を実運用レベルで完成させた話（data.fields[] の読み解きが山場）

問い合わせフォームが届いても誰も気づかない、転記漏れが起きる——中小企業の現場でよくある話です。この記事では、無料のフォームツール「Tally」と自動化ツール「Make」をつないで、フォーム送信から担当者へのメール通知までを自動化した実際の作業記録を共有します。特につまずいた「配列（複数データの並び）の番号指定」の部分を、再現できる粒度で書きます。

## なぜフォーム→通知の自動化なのか

製造業の現場で働きながらAI・自動化の研修をしていると、相談の入口はだいたい同じです。

- 問い合わせメールが特定の人の受信箱に埋もれる
- フォームの内容を手でExcelに転記している
- 「見た／見てない」が口頭確認になっている

この手の作業は、AIを入れる前に「つなぐ」だけで解決することが多いです。今回使ったのは以下の2つ。

- **Tally**：無料枠が広いWebフォーム作成ツール。Googleフォームに近い感覚で作れます。
- **Make**（旧Integromat）：ツール同士を線でつなぐ自動化サービス。「Aが起きたらBをする」をGUIで組めます。

今回のゴールは「Tallyのフォームが送信されたら、入力内容が入った状態のメールが自動で飛ぶ」こと。テスト用のダミーデータではなく、**実フォームからの実データで動く状態**まで持っていきます。

## 実際にやった手順

前提として、Make側にはPhase 1〜2でWebhook（Webの出来事を受け取る受付窓口のURL）を使ったシナリオを作ってある状態からのスタートです。

1. **MakeでWebhookモジュールを作成し、URLをコピーする**
   Makeの新規シナリオで最初のモジュールに「Webhooks → Custom webhook」を選び、生成されたURLを控えます。これが「Tallyからの連絡先」になります。

2. **TallyでフォームをつくりWebhookを登録する**
   Tallyのフォーム編集画面から Integrations（連携設定）→ Webhooks を開き、先ほどのURLを貼り付けます。これで「フォームが送信されたらこのURLに中身を送る」設定になります。

3. **Makeを待ち受け状態にして、フォームをテスト送信する**
   Makeの「Run once」を押して待ち受けにし、その状態で実際にTallyのフォームを自分で送信します。ここが重要で、**Makeは実際に一度データを受け取らないと、どんな形のデータが来るのかを覚えてくれません**。

4. **受信したデータ構造を確認する**
   送信に成功すると、Webhookモジュールに受け取った中身が表示されます。ここでTallyのデータの形が見えてきます。

5. **メール送信モジュールを追加し、内容を差し込む**
   Webhookの後ろに Email → Send an email をつなぎ、宛先・件名・本文を設定。本文に、受け取ったフォームの値を「タグ」（変数の差し込み）として埋め込みます。

6. **もう一度フォームから送信して、中身入りのメールが届くか確認する**

## つまずいた点と解決：値が空のメールが届く

ここが今回の山場でした。

メール送信の設定画面で、Makeが提示してくるタグを本文にドラッグして入れ、テスト送信。届いたメールを開くと——**名前も問い合わせ内容も空欄**。メール自体は届いているので、つながってはいる。でも中身が入らない。

原因はTallyのデータ構造にありました。Tallyは、フォームの各項目を**`data.fields[]` という配列（複数の項目が順番に並んだリスト）**で送ってきます。項目ごとに「名前用のキー」「内容用のキー」が用意されているわけではなく、こういう形です。

```
data
 └ fields   ← 配列
     [0] label: "メールアドレス"   value: "..."
     [1] label: "お名前"           value: "..."
     [2] label: "お問い合わせ内容" value: "..."
```

つまり、`data.fields.value` のような指定では、どの項目のことか決まりません。**何番目の項目か（配列番号）を指定する必要がある**わけです。

解決策は、Makeのタグ指定を配列番号つきに書き換えることでした。

- 名前 → `fields[1].value`
- 問い合わせ内容 → `fields[2].value`

Makeのマッピング欄では、タグを一度入れてから角カッコの中の番号を手で書き換えられます。番号は **0から始まる** 点に注意です。上から1番目の項目は `[0]`、2番目が `[1]` になります。

この修正後にもう一度フォームを送信したところ、名前と問い合わせ内容がきちんと入ったメールが届きました。ここで初めて「実運用レベル」と言える状態になった実感がありました。

### なぜ最初にこれで詰まったか

振り返ると、原因は「画面に出てきたタグをそのまま使えば動くはず」と思い込んでいたことです。自動化ツールはGUIで組めるぶん、**データがどんな形で流れているかを見ないまま進めてしまいがち**です。

対策はシンプルで、**メール送信を組む前に、Webhookが受け取った生データを一度じっくり眺める**こと。Makeは受信内容をツリー表示してくれるので、そこで「fieldsは配列になっているな」「お名前は上から2番目だな」と確認してから、後段のモジュールを組めば手戻りがありません。

## この自動化が実務で解決すること

小さな仕組みですが、現場に置くと効きます。

- **問い合わせの見落としがなくなる**：個人の受信箱ではなく、共有アドレスや複数名に同時通知できます。
- **転記がなくなる**：メール本文のフォーマットを固定できるので、そのまま台帳に貼れます（この先Googleスプレッドシートに直接追記する分岐も足せます）。
- **窓口を統一できる**：電話・FAX・メールでバラバラに来ていた問い合わせを、フォーム1本に寄せる口実になります。

そして何より、**「つなげば動く」という体験を社内で共有できる**のが大きいです。AI導入の相談を受けると、いきなり生成AIの話になりがちですが、手前の「情報が人の手で運ばれている」部分を自動化するほうが、費用対効果も納得感も高いケースが多いと感じています。

## 明日から使えるチェックリスト

Tally × Make でフォーム通知を組むときの実践チェックリストです。

- [ ] Makeで Webhooks → Custom webhook を作り、URLをコピーした
- [ ] TallyのIntegrations → WebhooksにURLを貼った
- [ ] Makeを「Run once」で待ち受けにしてから、実際にフォームを送信した
- [ ] **メールを組む前に**、受信データのツリーを開いて構造を確認した
- [ ] `data.fields[]` が配列になっていることを確認した
- [ ] 各項目が上から何番目か（**0始まり**）をメモした
- [ ] メール本文のタグを `fields[1].value` のように配列番号つきで指定した
- [ ] 修正後にもう一度フォームから送信し、**中身が入った状態**でメールが届くのを確認した
- [ ] 本番投入前に、フォームの項目を増減すると番号がずれることをチームに共有した

最後の項目は特に重要です。フォームに項目を1つ追加すると、それ以降の配列番号がすべてずれます。「フォームをいじったら通知の中身も必ず再テスト」をルールにしておくと安全です。

## まとめ

Tallyのデータは `data.fields[]` という配列で届くため、メールに値を差し込むには配列番号での指定が必要でした。
GUIツールでも、一度は生データの構造を自分の目で確認するのが最短ルートです。
フォーム→通知の自動化は小さな一歩ですが、見落としと転記という現場の地味な負担を確実に減らします。
