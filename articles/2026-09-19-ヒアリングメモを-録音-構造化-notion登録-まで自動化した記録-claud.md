# ヒアリングメモを「録音→構造化→Notion登録」まで自動化した記録（Claudeスキル化・iPhone移植まで）

AIコンサルや業務改善の現場では、ヒアリングの内容をどう残すかで、その後の提案の質が決まります。この記事は、自作のヒアリングメモアプリにNotion連携を足し、Claudeのスキルとして呼び出せるようにし、さらにiPhoneでも使えるように移植した実際の作業ログをまとめたものです。同じように「聞いた話がメモのまま死蔵されている」人の参考になればと思います。

## そもそも何が困っていたのか

製造業の現場で働きながら、副業でAIコンサル・研修をしています。困っていたのは大きく3つでした。

- **ヒアリング直後のメモがバラバラ**。手書きノート、スマホのメモアプリ、打ち合わせ後に思い出して書いたSlackの下書き。置き場所が統一されていない。
- **形式が毎回違う**。同じ「現場の困りごと」を聞いているのに、人によって書く深さが違い、後から比較できない。
- **聞いた内容を提案に変換する手間が毎回ゼロから**。前回どんな課題を聞いたかを探すところから始まる。

つまり、ヒアリングは「一次情報の宝庫」なのに、**構造化されていないせいで資産にならない**という状態でした。ここを直すのが今回の目的です。

## 作ったものの全体像

最終的に、次の4つを組み合わせた導線になりました。

1. **ヒアリングメモアプリ（自作）** — 聞くべき項目をフォーム化したもの。今回、項目を追加して精度を上げました。
2. **Notionデータベース** — メモの保存先。Notionの「データベース」は、Excelの表のように行（1件のヒアリング）と列（項目）で管理できる仕組みです。
3. **Claudeのスキル化** — Claude（対話型AI）に「この手順でヒアリングメモを整形しろ」という手順書を登録しておき、毎回プロンプトを書き直さなくても同じ品質で処理できるようにする仕組みです。
4. **iPhoneアプリへの移植** — 現場や移動中でも使えるように、スマホから入力・確認できるようにしました。

これで、**ボイスメモで録音 → 文字起こし → Claudeが構造化 → Notionに登録**という一本道ができました。

## 実際にやった手順

真似できる粒度で書きます。ツールは同じでなくても、考え方は流用できます。

1. **先に「項目」を紙に書き出す**。アプリやDBを作る前に、ヒアリングで必ず聞くことを列挙します。私の場合は、既存アプリを使う中で「これも毎回聞いているのに項目化していない」ものが出てきたので、そこを追加しました。
2. **Notionでデータベースを作る**。列（プロパティ）は、1で出した項目に対応させます。ここで大事なのは**型を決めること**。会社名はテキスト、業種はセレクト（選択肢）、課題の緊急度はセレクト、ヒアリング日は日付、といった具合です。何でもテキストにすると後で絞り込めません。
3. **Notion側のAPI連携を用意する**。NotionのインテグレーションをつくってAPIキーを発行し、対象のデータベースにそのインテグレーションを「接続」します。ここを忘れると、キーが正しくてもDBが見えません（後述）。
4. **Claudeのスキルとして手順を固定する**。「文字起こしテキストを受け取る → 指定の項目に分解する → 不明な項目は空欄にし、勝手に埋めない → JSON形式で出力する」という手順書を書いてスキル化しました。**推測で埋めさせない**指示は必須です。
5. **アプリからNotionへ登録する処理をつなぐ**。構造化された結果をNotionのページとして作成します。
6. **iPhoneに移植する**。ボイスメモを録って、その場で流し込めるところまで持っていきました。現場の駐車場で車に戻った直後に処理できるのが、実運用では一番効きます。

## つまずいた点と解決

**1. 項目を最初から完璧に設計しようとして止まった**

「聞くべきこと」を最初に全部決めようとすると、いつまでも作り始められません。結局、一度作って使い、足りないと気づいた項目を後から足す形になりました。**DBの列は後から足せる**ので、最小限で走らせたほうが早いです。

**2. NotionのAPIで「データベースが見つからない」**

APIキーもデータベースIDも合っているのにエラーになる。原因は、作ったインテグレーションを対象DBに接続していなかったことでした。Notionは「キーを持っている＝アクセスできる」ではなく、**DBごとに共有（コネクト）を許可する**仕様です。ここは最初に必ず確認してください。

**3. プロパティの「型」の食い違い**

セレクト型の列に、存在しない選択肢の文字列を送るとエラーになったり、意図しない値が増えたりします。対策として、Claude側のスキルに**選択肢の候補リストを明記**し、「この中から選ぶ。該当なしはその他」と指示しました。AIの出力を受け取る側のルールを、AIに先に教えておくイメージです。

**4. 文字起こしが構造化しづらい**

会話の文字起こしは、言い直しや雑談が混じるので、そのままでは項目に収まりません。ここもスキル側で「雑談・挨拶は除外」「発言者が誰かを推測しない」といったルールを足して安定させました。

**5. 移植したら入力が面倒になった**

PCで作ったものをそのままスマホに持っていくと、入力欄が多くて指で打つ気が失せます。だから**スマホ側は「録音して投げる」を主役**にし、細かい修正はNotion上で後からやる、と役割を分けました。

## 明日から使えるチェックリスト

- [ ] ヒアリングで毎回聞いていることを、まず10個ほど紙に書き出す
- [ ] その10個をNotionのデータベースの列にする（型を決める：テキスト／セレクト／日付）
- [ ] セレクト型の選択肢は、実際に使いそうな5つ程度から始める

- [ ] AIへの指示に「不明な項目は空欄。推測で埋めない」を入れる
- [ ] AIへの指示に「選択肢はこの中から選ぶ」と候補リストを明記する
- [ ] まずは1件、自分の過去のヒアリングで通しテストする
- [ ] スマホからは「録音を投げるだけ」にして、編集はPC/Notionで行う
- [ ] 使ってみて足りない項目が出たら、その場で列を追加する

## まとめ

ヒアリングは聞いた瞬間が価値のピークで、そこから構造化されないまま時間が経つと急速に劣化します。今回やったのは、録音から構造化、保存までの摩擦をできるだけ減らすことだけです。項目設計は最小限で始め、Notion側の接続設定とAIへの「推測禁止」ルールだけ先に固めれば、同じ導線は十分に再現できます。
