# Make（旧Integromat）で問い合わせフォームを自動振り分けする：Router＋フィルター実装と403エラーの直し方

「問い合わせメールを見て、資料請求か一般質問かを判断して、それぞれ違う返信を送る」——この地味な作業を自動化した記録です。ノーコードツールMakeを使い、実際にハマった403エラーの解決までを、再現できる粒度で書きます。中小企業で「問い合わせ対応が属人化している」方向けの内容です。

## なぜ問い合わせの「振り分け」から手をつけたのか

私は製造業の現場で働きながら、副業でAI活用の相談を受けています。相談の入り口はたいていWebフォームからの問い合わせですが、内容は大きく2種類に分かれます。

- **資料請求**：サービス概要のPDFを送ってほしい
- **一般の問い合わせ**：料金や日程、内容の質問

やることは決まっているのに、毎回メールを開いて内容を読み、テンプレートを探して、貼り付けて送る。1件3分でも、積もると馬鹿になりません。しかも夜間や現場作業中は返信が数時間遅れます。**判断基準が明確で、パターンが少ない作業**は自動化の適性が高い。ここが最初の一歩として妥当だと考えました。

使ったのは **Make（旧Integromat）**。プログラムを書かずに、アプリ同士を線でつないで処理の流れを組み立てるツールです。同種のZapierと比べて、条件分岐を視覚的に組みやすいのが選定理由でした。

## 全体の設計：Routerで道を分ける

Makeでは、処理のかたまりを「モジュール」と呼び、それを左から右へつないでいきます。今回作ったのはこの流れです。

1. **トリガー**：フォーム送信を受け取る（新しい問い合わせが来たら動き出す）
2. **Router（ルーター）**：ここで道を2本に分岐させる
3. **ルートA**：資料請求 → 資料リンク付きの返信をGmailで送信
4. **ルートB**：それ以外 → 一般問い合わせ用の返信をGmailで送信

ポイントは **Router** です。Routerを1つ置くと、そこから複数のルートが枝分かれします。そして**各ルートの根元に「フィルター」を設定**することで、「この条件に当てはまるデータだけ、この道を通る」という制御ができます。

分岐の考え方は、現場の作業指示書と同じです。「この条件ならAの手順、それ以外はBの手順」。これをツール上で表現しているだけ、と捉えると理解が早いはずです。

## フィルターの条件設計で最初につまずいた

最初、フィルターの条件をこう組みました。

- ルートA：問い合わせ種別が「資料請求」と**完全一致**（Text operators: Equal to）
- ルートB：問い合わせ種別が「一般」と完全一致

テストしてみると、**どちらのルートも通らない問い合わせ**が出ました。原因は単純で、フォームの選択肢に無い、自由入力に近い内容が混ざっていたためです。完全一致だけで組むと、想定外の値がどこにも流れず**消える**。自動化としては最悪の失敗で、届いたはずの問い合わせに誰も気づかない状態になります。

修正した設計はこうです。

- **ルートA**：資料請求の条件に合致するとき（`contains`＝含む、を使い「資料」というキーワードで拾う）
- **ルートB**：**フィルターに「Fallback route」を設定**し、Aに当てはまらなかったものを全部受ける

Makeでは、Routerから伸びるルートの1本を「フォールバック（受け皿）ルート」として指定できます。**条件から漏れたデータの行き先を必ず用意する**。これは自動化の鉄則だと痛感しました。現場でいう「不適合品の置き場を決めておく」のと同じ発想です。

もう一点、Routerのルートには**実行順序**があります。上から順に条件が評価され、フォールバックは常に最後に判定されます。条件が重なりうる場合は、**より限定的な条件を上に置く**のが安全です。

## 403エラー：Gmail連携で止まった話

一番時間を取られたのが、Gmail送信モジュールで出た **403エラー**でした。Makeの実行ログに赤いエラーが出て、メールが送られません。

403は「認証はできているが、その操作をする権限がない」という意味のエラーコードです。つまり**ログインは通っているのに、送信の許可が下りていない**状態。原因は **OAuthのスコープ（許可範囲）** でした。

Googleアカウントと外部サービスを連携するとき、「メールを読む権限だけ」「送信する権限も含む」といった具合に、許可する範囲が細かく分かれています。私は最初の接続作成時に、読み取り系の権限だけで接続を作ってしまっていました。だから「取得」はできても「送信」で弾かれたわけです。

解決手順は以下の通りです。

1. Makeの左メニューから **Connections（接続）** を開く
2. 該当のGoogleの接続を**いったん削除**する（既存接続を編集するより、作り直したほうが確実でした）
3. Gmailモジュールに戻り、**Add（新規接続を作成）** を選ぶ
4. 認証画面で、**要求されている権限のチェックを全部オンにする**（ここを飛ばすと同じエラーが再発します）
5. 接続完了後、モジュール単体で **Run this module only** を実行し、送信できるか確認

補足として、Googleの認証画面で「このアプリは確認されていません」という警告が出ることがあります。慌てずに「詳細」→「（アプリ名）に移動」から進めば認証できます。ただし、**自社のGoogle Workspaceで管理者が外部アプリを制限している場合は、管理者側の許可が必要**です。会社のアカウントでうまくいかないときは、まず情報システム担当に確認するのが早道です。

## つまずいた点と解決

実際に詰まったのは、大きく3つでした。

**1. フィルター条件から漏れたデータが消えた**
→ Routerのルートの1本を **Fallback route** に設定。条件に合わないものは必ずここへ流れるようにしました。「想定外は必ず受け皿へ」。

**2. Gmail送信で403エラー**
→ 原因はOAuthスコープ不足。接続を削除して作り直し、認証画面で**全ての権限にチェック**を入れて解決しました。エラーコードが403なら「認証（ログイン）」ではなく「認可（権限）」を疑うのが近道です。

**3. テストのたびに本番メールが飛びかける**
→ 送信先を自分のアドレスに固定してテストしました。Makeには手動で1回だけ動かす **Run once** があるので、いきなり自動実行（Scheduling ON）にしないこと。これを怠ると、テストメールが顧客に届く事故につながります。

## 明日から使えるチェックリスト

Makeで問い合わせ自動振り分けを作るときの手順です。

- [ ] **手作業を先に文章化する**：「◯◯なら返信A、それ以外は返信B」と紙に書く。ここが曖昧なまま作り始めると必ず迷います
- [ ] **分岐は最初2本まで**にする。3本以上は動いてから増やす
- [ ] Routerを置いたら、**必ず1本をFallback routeに指定**する
- [ ] 条件は完全一致（Equal to）より **contains（含む）** から検討する
- [ ] 条件が重なる可能性があるなら、**限定的な条件を上のルートに**置く
- [ ] Gmail接続でエラーが出たら、**403＝権限不足**を疑い、接続を作り直して全スコープを許可する
- [ ] テスト中は**送信先を自分のアドレス**に固定する
- [ ] 各モジュールは **Run this module only** で単体確認してから全体を通す
- [ ] 全体テストは **Run once** で。自動実行のONは最後
- [ ] 返信テンプレートには「自動返信です。詳細は追ってご連絡します」の一文を入れる（人が見ている安心感を残すため）

## まとめ

Routerとフィルターの組み合わせは、現場の作業指示書をそのままツールに移す作業でした。
最大の学びは「条件から漏れたデータの行き先を必ず作る」こと、403は認証ではなく権限を疑うこと。
判断基準が明確でパターンが少ない作業から手をつけると、自動化は失敗しにくいと感じています。
