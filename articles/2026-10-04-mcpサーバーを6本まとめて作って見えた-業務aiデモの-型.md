# MCPサーバーを6本まとめて作って見えた、業務AIデモの「型」

「AIを業務に使いたいが、何から作ればいいか分からない」という相談をよく受けます。この記事では、製造業の現場で働きながらAI研修・コンサルをしている筆者が、MCPサーバーのデモを6本まとめて作り切った経験から、業務AIの最初の一歩をどう設計するかを共有します。2026年10月2日時点の、あくまで「デモを作り切った」段階の一次情報です。

## そもそもMCPとは何か

MCP（Model Context Protocol）は、ChatGPTやClaudeのような生成AIに「外部の道具」を使わせるための共通規格です。AIは文章を作るのは得意ですが、そのままでは予約表に書き込んだり、社内のデータベースを検索したりはできません。そこで「予約を登録する」「在庫を調べる」といった機能を小さなサーバーとして用意し、AIから呼び出せるようにする——その接続口の決まりごとがMCPです。

現場の感覚で言うと、**AIという汎用の作業者に、専用治具を渡すようなもの**です。汎用機そのものを改造するのではなく、治具側を業務に合わせて作る。だから「この会社のこの業務でしか意味がない機能」ほど、MCPで作る価値が出ます。

## 作った6本と、それぞれが向き合う業務課題

今回、ロードマップに積んでいたMCPサーバーを全件実装しました。それぞれテスト付きです。

1. **LINE予約・配信** — 電話とLINEで来る予約を人が転記している店舗・サービス業向け
2. **写真→見積** — 現場写真から見積の下書きを起こす、建設・修繕・設備系の課題
3. **家計見直し** — 支出データを分類して見直し候補を出す、個人向けの相談業務
4. **問題バンク** — 研修や試験の問題を蓄積・再利用する、教育・社内研修向け
5. **交流会マッチング** — 参加者同士の組み合わせを提案する、コミュニティ運営向け
6. **交流会カレンダー** — イベント日程の管理・案内を扱う、同じくコミュニティ運営向け

並べてみると、ジャンルはバラバラです。ただし共通点がひとつあります。**どれも「人が手で転記・分類・突き合わせをしている工程」を狙っている**ことです。AIらしい高度な判断ではなく、地味な中継作業を奪いに行っている。これは意図したというより、6本作り終えてから気づいた共通点でした。

## 6本続けて作って見えた「型」

1本目と6本目では、着手してから動くまでの早さがまったく違いました。理由は、作業が型になったからです。具体的には次の順序です。

1. **入力と出力を一文で書く**（例：「写真を受け取り、見積項目の候補を返す」）
2. **扱うデータの形を先に決める**（予約なら日時・氏名・人数・連絡先、のように項目を列挙する）
3. **ツールの名前と引数を決める**（AIから見て何をする道具なのかが名前で分かるようにする）
4. **先にテストを書く**（正常系に加え、空の入力・想定外の値を1つずつ）
5. **実装してテストを通す**
6. **実際にAIから呼び出して、AIが意図通りに道具を選ぶか確認する**

ポイントは5ではなく**6まで必ずやる**ことです。テストが通ってもAIがその道具を使ってくれないことがあります。原因はたいていコードではなく、ツール名や説明文が曖昧で、AIが「これは今の用件に使う道具だ」と判断できていないことでした。

## つまずいた点と解決

### 1本目で「機能を盛る」病が出た

最初のデモは、思いついた機能を全部入れようとして手が止まりました。予約を受けるなら変更も、キャンセルも、リマインドも……と広げた結果、どこから作るか決められなくなる。

解決策は単純で、**「このデモで証明したいことは一文で何か」を先に紙に書く**ようにしました。LINE予約なら「LINEの文面から予約データを作れる」。それ以外は後回しです。デモは全機能を揃える場ではなく、成立することを見せる場だと割り切ってから、速度が戻りました。

### テストを後回しにすると、修正が怖くなる

途中で仕様を変えたとき、テストがないデモは「直したつもりが別のところを壊していないか」が分からず、手が止まりました。以降は**小さくてもいいので先にテストを書く**ことを徹底しました。全部の分岐を網羅する必要はなく、正常系1本と異常系1〜2本で、直す勇気はかなり違います。

### AIが道具を使ってくれない

前述の通り、実装は正しいのに呼ばれないケースがありました。対処は、ツールの説明文を**「いつ使うか」から書き直す**ことです。「予約を登録します」ではなく「利用者が日時と人数を伝えてきたときに、予約を登録します」と書く。人に作業指示を出すときと同じで、使う場面が書いていない手順書は使われません。

## 明日から使えるチェックリスト

AIを業務に組み込むデモを1本作るとき、以下をそのまま使えます。

- [ ] この仕組みで**置き換えたい手作業**を1つだけ挙げた（転記・分類・突き合わせから探す）
- [ ] 入力と出力を**一文**で書いた
- [ ] 扱うデータ項目を**箇条書きで列挙**した（曖昧な項目は削る）
- [ ] 道具の名前が、**名前だけで役割が分かる**ものになっている
- [ ] 説明文に「**いつ使うか**」が書いてある
- [ ] 正常系テスト1本＋異常系テスト1〜2本を**先に**書いた
- [ ] テスト通過後、**実際にAIから呼び出して道具を選ぶか**確認した
- [ ] 「今回やらないこと」を紙に書いて、机の横に貼った

## まとめ

MCPデモを6本続けて作ると、業務が違っても手順は同じ型に収束しました。
狙うべきは高度な判断ではなく、人が手で転記・分類している地味な中継工程です。
現時点はデモ完成段階であり、実際の業務データでどこまで持つかは、これからの検証課題です。
