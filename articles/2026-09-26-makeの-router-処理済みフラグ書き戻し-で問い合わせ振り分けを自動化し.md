# Makeの「Router＋処理済みフラグ書き戻し」で問い合わせ振り分けを自動化した記録

問い合わせフォームの内容をスプレッドシートで受けているものの、種類ごとの返信を手作業でやっている——そんな中小企業の現場向けの記事です。ノーコード自動化ツール「Make」で、**条件によって処理を分岐させ、終わった行に「済」を書き戻す**ところまで作ったので、そのままの手順とつまずきを共有します。

## 作ったもの：問い合わせ自動処理シナリオ

学習テーマは「Make Phase 2」。Phase 1（トリガー→1本道のアクション）から一歩進んで、次の2つを組み合わせました。

- **Router（ルーター）** — 1つの流れを条件ごとに枝分かれさせるモジュール。「資料請求」と「一般問い合わせ」で送るメールを変える。
- **Update a Row** — Googleスプレッドシートの**既存の行を書き換える**モジュール。処理が終わった行に「済」フラグを立てる。

流れにするとこうです。

1. スプレッドシートに追加された問い合わせ行を検知
2. Routerで「資料請求」か「一般」かを判定
3. それぞれに対応したメールを送信
4. 元の行の「ステータス」列に「済」と書き戻す

Phase 1の一本道と決定的に違うのは、**4番目の「書き戻し」がある**点です。これがないと、シナリオが再実行されるたびに同じ人へ何度もメールが飛びます。自動化を「業務で使えるもの」にするかどうかの分かれ目が、ここにありました。

## 手順：Routerと書き戻しの組み立て方

再現できる粒度で書きます。

1. **トリガーを置く**：Google Sheetsの行取得モジュールで、問い合わせが溜まるシートを指定します。
2. **Routerを挿入する**：トリガーの後ろに Router を追加。線が枝分かれします。
3. **各ルートにフィルタを設定する**：枝分かれした線のレンチアイコンからフィルタを開き、条件を書きます。今回は「問い合わせ種別」列が `資料請求` と等しい／そうでないもの、という形です。
4. **各ルートにメール送信モジュールを置く**：資料請求ルートには資料ダウンロードリンク入りの文面、一般ルートには受付連絡の文面。差出人名や件名も分けます。
5. **各ルートの末尾に Update a Row を置く**：ステータス列に「済」をセット。ここで**行番号の指定**が必要になります（後述）。
6. **1件だけで実行テストする**：テスト行を1行だけ入れて Run once。メールが届くか、シートの該当行に「済」が入るかを目視確認します。

ポイントは、**書き戻しモジュールを各ルートの末尾に置く**こと。Routerの手前に置くと分岐前に「済」がついてしまい、メール送信が失敗しても済扱いになります。

## つまずいた点と解決

### 1. Update a Row が「どの行を更新すればいいか」分からない

最初に詰まったのがこれです。Update a Row には Row number（行番号）の入力欄があるのですが、問い合わせ内容そのものには行番号という情報がありません。手で「5」と打てばテストは通りますが、それでは毎回5行目を書き換えるだけの使い物にならない設定になります。

**解決**：前のモジュール（行を取得するモジュール）の出力に **`Row number` というタグ**が含まれているので、それをマッピングします。Makeの入力欄をクリックすると右側に前段モジュールの出力タグ一覧が出るので、そこから `Row number` をドラッグして入れるだけです。「自分で行番号を計算しなきゃいけないのでは」と身構えていましたが、**ツール側がすでに持っている情報を渡すだけ**でした。

### 2. どのルートにも当てはまらないデータが消える

Routerのフィルタは「条件に合ったものだけ通す」仕組みです。つまり、種別欄が空白だったり、想定外の値（たとえば「その他」）が入っていたりすると、**どのルートにも入らず、エラーも出さずに何も起きない**。これは実務ではかなり怖い挙動です。「動いているように見えて、一部の問い合わせが黙って落ちている」状態になります。

**解決**：**Fallback（フォールバック）ルート**の設定を学びました。フィルタ設定画面で Fallback route を有効にすると、「他のどのルートにも該当しなかったもの」が必ずそこへ流れます。今回はここに「担当者へ手動確認を依頼する通知」を置く想定で組みました。

現場の言い方に直すと、**不良品を弾くラインに「判定不能品の受け皿」を必ず1つ置く**のと同じ発想です。自動化の設計では、正常系よりもこの「どれでもない」の受け皿を先に決めたほうが安全だと実感しました。

## この自動化が解決する実務の課題

- **二重送信の防止**：処理済みフラグがあるので、シナリオを再実行しても同じ行は対象外にできます。
- **属人化の解消**：「資料請求ならこの文面」という判断が、担当者の頭の中からシナリオ上のフィルタ条件へ移ります。担当者が休んでも回ります。
- **進捗が目で見える**：シートのステータス列を見れば、未処理が何件残っているか一目で分かります。自動化していても「今どこまで進んだか」が見えることが、現場の安心感につながります。

## 明日から使えるチェックリスト

Makeで分岐つき自動化を組むときの確認項目です。

- [ ] 元データ（シート等）に**ステータス列**を用意したか
- [ ] 書き戻しモジュールは**各ルートの末尾**に置いたか（分岐前に置いていないか）
- [ ] Update a Row の行番号に、前段モジュールの **`Row number` タグ**をマッピングしたか（固定値のままになっていないか）
- [ ] **Fallback ルート**を設定し、想定外データの行き先を決めたか
- [ ] 種別欄が**空白**のテストデータで動かしてみたか
- [ ] 本番投入前に、テスト行1件だけで Run once して結果を目視したか
- [ ] メール送信先を、テスト中は自分のアドレスに向けているか

## まとめ

Routerで分岐、Update a Rowで「済」を書き戻す——この2つが揃うと、自動化は「動くデモ」から「業務で回せる仕組み」に変わります。
つまずきは、行番号の指定方法と、どこにも該当しないデータの扱いの2点でした。
まずは1シナリオ、テスト行1件から試すのがおすすめです。
