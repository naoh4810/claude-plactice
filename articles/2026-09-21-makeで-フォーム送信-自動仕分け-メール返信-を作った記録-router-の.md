# Makeで「フォーム送信→自動仕分け→メール返信」を作った記録：Router のフィルタが両ルート0件になった原因は「演算子の選び間違い」でした

ノーコード自動化ツール Make（旧 Integromat）で、Tally フォームの送信をきっかけに問い合わせ内容を自動で振り分け、それぞれに合ったメールを送る仕組みを作りました。この記事は、実際に手を動かして完成させたときの手順と、途中で 1 時間ほど止まったつまずき（Router のフィルタが両ルートとも0件になる）を、その原因と解決まで含めて記録したものです。問い合わせ対応を人力でさばいている中小企業の担当者の方に向けています。

## 今回作ったシナリオの全体像

構成はシンプルです。

```
Tally（フォーム送信）
   ↓ Webhook で受信
Make の Router（分岐）
   ├─ ルート1：資料請求 → 資料ダウンロードリンク入りのメール
   └─ ルート2：一般問い合わせ → 受付完了のお礼メール
```

Make の学習では、条件分岐（Phase 2）とフォーム連携（Phase 3）を別々に練習していました。今回はその 2 つを合体させた「集大成」として、一本のシナリオに仕立てています。

ポイントは、**分岐の判定材料をフォーム側で用意しておく**ことです。フォームに「お問い合わせ種別」のような選択式の項目を 1 つ置いておくと、Make 側の条件式が一気に簡単になります。自由記述文から意図を推測させようとすると、途端に難易度が上がります。

## 手順：Tally → Webhook → Router → メール

1. **Tally でフォームを作る**
   氏名・メールアドレスに加えて、分岐用の選択項目（例：「資料請求」「その他のお問い合わせ」）を必須で入れます。選択肢の文字列は後で条件式にそのまま書くので、表記を控えておきます。
2. **Make で新規シナリオを作り、Webhook モジュールを置く**
   「Custom webhook」を追加して URL を発行します。Webhook とは、簡単に言うと「相手側で何かが起きたら、この URL に中身を送ってね」という受け取り口です。
3. **Tally 側の Integrations に Webhook URL を貼る**
   設定したら、**必ずテスト送信を 1 回行います**。Make 側が「Determine data structure（データ構造の判定）」状態で待っているうちに送信しないと、後の工程で項目名が選べません。ここは私も一度やり直しました。
4. **Router を追加し、ルートを 2 本引く**
   Router は分岐器です。ルートごとに「フィルタ（Set up a filter）」を設定します。
5. **各ルートにフィルタ条件を設定する**
   ルート1は「お問い合わせ種別 = 資料請求」、ルート2はそれ以外。ルート2は「Fallback route（どれにも当てはまらなかったとき用）」にしておくと取りこぼしが出ません。
6. **各ルートの先にメール送信モジュールを置く**
   宛先にはフォームのメールアドレス項目をマッピングし、本文の書き出しに氏名を差し込みます。
7. **「Run once」でテスト実行し、実際にフォームから 2 パターン送信して確認する**

## つまずいた点と解決：両ルートとも 0 件になった

組み上げて実行したところ、**Router から先が両方とも動かない**という状態になりました。Webhook までは正常にデータが届いているのに、ルート1もルート2も通過件数が 0。フィルタが「全部はじいている」状態です。

最初は条件に書いた文字列のタイポ（全角・半角、余分なスペース）を疑いました。しかしコピペし直しても改善しません。

原因は、**フィルタの演算子（Operator）で「Array operators」を選んでいた**ことでした。Make のフィルタ設定では、演算子のプルダウンが

- Basic operators（基本）
- Text operators（テキスト）
- Numeric operators（数値）
- Date & time operators（日時）
- **Array operators（配列）**

といったカテゴリに分かれています。この中に「contains」「equal to」といった似た名前の項目がそれぞれ存在します。私は一覧から目についた `contains` を選んでいたのですが、それは配列（複数の値がまとまったリスト）用の演算子でした。比較対象は単なるテキストなので、配列として評価された瞬間に条件が成立せず、静かに全件はじかれていた、というわけです。

**解決方法は、演算子を Text operators の `Contains`（または `Equal to`）に選び直すだけ**でした。エラーメッセージは出ず、ただ 0 件になるだけなので気づきにくい種類のミスです。

ここから得た教訓は 2 つあります。

- **「0 件」はエラーではなく“条件が一致しなかった”というメッセージ**。まず疑うのは値ではなく条件の型（テキストなのか、配列なのか、数値なのか）。
- 切り分けは、**フィルタをいったん外して全部通す → 通るなら条件側が原因**、と機械的にやると速い。現場の設備トラブルで、まず電源とセンサーを切り分けるのと同じ発想です。

## この仕組みが解決する実務課題

この程度の自動化でも、効く場面ははっきりしています。

- **一次返信の遅れがなくなる**：担当者がメールに気づくまでの時間差がゼロになります。問い合わせ対応は「速さ」そのものが印象を左右します。
- **問い合わせ内容の仕分け作業が消える**：資料請求なのか、見積依頼なのか、人が読んで判断して転送する、という手間がフォーム設計の段階で片付きます。
- **属人化の解消**：「あの人が休むと問い合わせが溜まる」状態から抜け出せます。
- **記録が自然に残る**：手作業の転送と違い、いつ何が来て何を返したかがシナリオの実行履歴に残ります。

小さな会社ほど、問い合わせ対応は誰かの「気合い」で回っていることが多いものです。そこを 1 本のシナリオで置き換えられるのは、費用対効果が高い部類だと感じています。

## 明日から使えるチェックリスト

- [ ] フォームに**分岐用の選択項目**を 1 つ用意したか（自由記述で判定させない）
- [ ] 選択肢の文字列をメモし、条件式に**コピペで**入れたか
- [ ] Make 側を待機状態にしてから、フォームを**テスト送信**したか
- [ ] Router のフィルタで、演算子を **Text operators のもの**から選んでいるか（Array operators と取り違えていないか）
- [ ] どれにも当てはまらない場合の **Fallback route** を用意したか
- [ ] メール本文に、宛名・問い合わせ内容の差し込みを入れたか
- [ ] 2 パターン以上を**実際にフォームから送って**動作確認したか
- [ ] 通らないときは、まずフィルタを外して切り分けたか

## まとめ

Make の条件分岐とフォーム連携は、組み合わせると「受付から一次返信まで」を丸ごと自動化できます。つまずきの多くはエラーではなく「0 件」という静かな失敗で現れるので、値より先に演算子の種類を疑うのが近道です。まずは自社の問い合わせフォーム 1 本を、この構成で置き換えてみるところからで十分だと思います。
