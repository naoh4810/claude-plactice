# Claude Codeで「記事制作の工程」を分業化してみた──AIエージェント6ステップでコラム1本を納品するまで

社内報やオウンドメディアの記事づくりを「誰か手の空いた人がまとめて書く」状態で回している中小企業の方向けの記事です。製造業の現場で работаいている私が、Claude Codeを使って記事制作を6つの工程に分け、実際にAI議事録作成のコラムを1本、図解入りHTMLまで仕上げた記録をまとめます。

※冒頭に誤字が入りました。「働いている」です。そのまま残しておきます。AIに書かせた原稿でも、こういうミスは人が見ないと残ります。

## なぜ「1回のプロンプトで記事を書かせる」のをやめたのか

最初にやったのは、よくあるやり方でした。「AI議事録作成について2500字のコラムを書いて」と一発で投げる方法です。

出てくるものは、読めます。文法も整っています。でも現場で使えませんでした。理由は3つです。

- **誰に向けた記事なのかが最後まで曖昧**。一般論が並ぶだけで、自社の読者像とズレる。
- **修正指示がしづらい**。全体を書き直させるか、自分で手直しするかの二択になる。
- **品質のばらつきが読めない**。同じ指示でも、日によって出来が違う。

製造業の感覚で言うと、これは「1人の職人が設計から加工から検査まで全部やっている」状態です。属人的で、どこで品質が落ちたか追えない。だったら工程を分けて、それぞれに担当を立てればいい。そう考えて、Claude Code上で記事制作を分業化するワークフローを組みました。

## 組んだのは「ヒアリング→構成→チェック→執筆→品質確認→納品」の6工程

実際に構築したフローはこうです。それぞれの工程を別のAIエージェント（役割を固定した指示セット）として定義し、前の工程の出力を次に渡していきます。

1. **ヒアリング** — 記事の目的、読者、盛り込む要素を質問形式で引き出す。ここでは書かせない。
2. **構成** — ヒアリング結果をもとに見出し構成と各ブロックの狙いを設計する。
3. **チェック（構成レビュー）** — 構成の段階で、読者像とのズレ、重複、抜けを指摘させる。
4. **執筆** — 承認済みの構成に沿って本文を書く。構成から逸脱しないことを条件にする。
5. **品質確認** — 事実関係、言い回しの重複、トーンの統一を確認する。
6. **納品** — 図解SVGの挿入とHTML化まで行い、そのまま公開できる形にする。

ポイントは**3番目の「構成チェック」を執筆の前に挟んだこと**です。ここを入れる前は、書き上がってから「そもそも構成が違う」と気づいて全部やり直していました。製造でいう後工程での手戻りと同じで、遅く見つかるほど高くつきます。

## 各工程で実際に効いた設定

### ヒアリング工程は「書かせない」と明示する

AIは放っておくと、質問しながら勝手に本文を書き始めます。なので、ヒアリング担当には「この工程では記事本文を一切書かない。質問と確認のみ」と明示的に禁止しました。これだけで、ヒアリングが質問として機能するようになります。

引き出す項目は固定しました。

- 想定読者（役職・知識レベル・抱えている課題）
- この記事を読んだ後に読者にどうなってほしいか
- 必ず盛り込む要素（自社の一次情報、実体験）
- 使ってはいけない表現・トーン

### 構成工程では「各見出しで何を言うか」まで書かせる

見出しだけ作らせると、執筆工程で中身が膨らみすぎたり薄すぎたりします。見出しごとに「ここで伝えること」を1〜2文で添えさせておくと、執筆のブレが減りました。

### 品質確認は「別の役割」として分ける

自分が書いた文章を自分でチェックさせても、AIは基本的に「良いと思います」と言います。工程として分け、「批判的に読む担当」と役割を与えると、指摘が出てくるようになりました。

## つまずいた点と解決

### 1. 工程間で情報が抜け落ちる

最初は各工程の出力を口頭（チャット上のやり取り）で渡していたため、ヒアリングで決めた「想定読者」が執筆工程に届かず、一般論の記事が出てきました。

**解決策**：工程ごとの出力をファイルに書き出し、次の工程はそのファイルを読ませる形に変えました。ヒアリング結果→構成→本文と、成果物が物として残るので、どこで情報が落ちたか後から追えます。これは製造の作業指示書と同じ考え方です。

### 2. 「チェック工程」が形だけになった

構成チェックを入れた当初、返ってくるのは「よく構成されています。このまま進めて問題ありません」ばかりでした。工程を置いただけでは機能しません。

**解決策**：チェックの観点を具体的に指定しました。「想定読者にとって不要なブロックを1つ以上挙げる」「見出し間で内容が重複している箇所を指摘する」「一次情報が入っていないブロックを列挙する」。**必ず何かを指摘させる形にする**と、実際に使える指摘が出るようになりました。

### 3. 図解SVGが本文と噛み合わない

納品工程で図解を入れようとして、先にSVG（テキストで書ける画像形式）を作らせたところ、本文の論旨とズレた図が出てきました。

**解決策**：図解は本文が確定してから、「この見出しの内容を1枚の図にする」と対象を限定して作らせました。図から作るのではなく、本文から図を起こす順番にすると噛み合います。

### 4. 出来上がったHTMLを自分で読まなかった

一番やらかしたのがこれです。HTML化まで自動で通したので満足してしまい、ブラウザで開いて読み返すのを後回しにしました。結果、言い回しの重複や、自分が普段使わない言葉遣いが残っていました。

**解決策**：納品工程の最後に「人間が通しで音読する」を工程として組み込みました。AIに任せる工程を増やすほど、最後の人間チェックの重みが増します。

## 明日から使えるチェックリスト

AIで記事や社内文書を作るときに、そのまま真似できる形にしました。

- [ ] 一発で書かせず、**最低でも「構成」と「執筆」を分ける**
- [ ] ヒアリング工程には「この工程では本文を書かない」と明示する
- [ ] 想定読者を「役職・知識レベル・課題」の3点で言語化する
- [ ] 構成は見出しだけでなく「各見出しで何を言うか」まで決める
- [ ] **執筆の前に構成をレビューする工程を挟む**（手戻りが一番安く済む場所）
- [ ] チェック工程では「必ず1つ以上指摘する」など、指摘を強制する観点を与える
- [ ] 各工程の出力はファイルに残し、次の工程に読ませる
- [ ] 図解は本文確定後に、対象の見出しを限定して作る
- [ ] 最後に必ず人間が通しで読む（できれば音読）

まずは「構成」と「執筆」を分けるだけでも変わります。工程を増やすのはその後で構いません。

## この仕組みが解決する実務の課題

中小企業で文書作成が滞る原因は、書く時間がないこと以上に、**書き始める前の「何を書くか」が決まっていないこと**だと感じています。構成工程を独立させると、ここを短時間で言語化できます。

もう一つは属人化の解消です。工程とチェック観点をファイルに残しておけば、別の担当者が同じ手順で同じ水準のものを作れます。品質が人ではなく手順に紐づく状態は、製造現場で標準作業を整備するのと同じ発想です。

なお、この仕組みで作れるのは「土台」までです。実体験や社内の一次情報は人間が入れるしかありません。AIが担うのは、それを形にする工程の方です。

## まとめ

記事制作を6工程に分け、Claude Code上で分業させたら、手戻りが減って図解入りHTMLまで一本通せました。
効いたのは工程を増やしたことより、**執筆前の構成レビューと、指摘を強制するチェック観点**でした。
最後に人間が通しで読む工程だけは、絶対に外さないでください。
