# Make の Webhook 実装でつまずいた3点と解決法：ポーリングとプッシュの違いを現場目線で理解する

ノーコード自動化ツール「Make」で、外部からのデータをリアルタイムで受け取る Webhook（ウェブフック）を実装しました。定時実行（ポーリング）との違いが腹落ちし、かつ実際に手が止まった箇所も3つありました。これから Make や Zapier で業務自動化を始める中小企業の担当者向けに、再現できる粒度で残しておきます。

## そもそも Webhook とは何か：工場の「呼び出しボタン」で考える

Webhook を説明するとき、私はいつも製造現場のアンドン（異常呼び出しランプ）に例えています。

自動化ツールのシナリオ（処理の流れ）を起動する方法は、大きく2つあります。

- **ポーリング（Polling）**：ツール側が定期的に「何か新しいデータある？」と聞きに行く方式。5分おき、15分おきといった設定をします。現場でいえば、班長が15分おきに各ラインを見回るイメージです。
- **プッシュ（Push / Webhook）**：データが発生した側から「今これが起きました」と通知が飛んでくる方式。作業者が異常時にボタンを押して、その瞬間にアンドンが光るイメージです。

Make の Webhook モジュールには「**Immediately as data arrives**（データが到着し次第すぐに）」というスケジュール設定があります。これがプッシュ型の実体で、待ち時間ゼロで起動します。

見回り型（ポーリング）は確実ですが、最悪15分遅れます。しかも何も起きていなくても見回りのたびに1回分の処理が消費されます。Make は月間の実行回数に上限があるプランが基本なので、ここは地味に効いてきます。呼び出しボタン型（Webhook）は、起きたときだけ動くので無駄がありません。

## 今回つくったもの：受信URL → Gmail送信

今回実装したシナリオは非常にシンプルです。

1. **Custom webhook** モジュールをシナリオの先頭（トリガー）に置く
2. Make が発行する受信用の URL をコピーする
3. その URL に、外部から `name` と `message` という2つの値を送る
4. 受け取った値を Gmail モジュールに差し込んで、メールを送信する

これだけです。ただ、この「これだけ」の中に、初見では気づきにくいポイントが詰まっていました。

### 実装手順

1. Make で新規シナリオを作成し、最初のモジュールで「Webhooks」→「Custom webhook」を選択します。
2. 「Add」を押して Webhook に名前を付けます（例：`test-hook`）。保存すると `https://hook.○○.make.com/xxxxxxxx` のような URL が発行されます。
3. この URL を**コピーしておきます**。これが受信の入り口です。
4. Make の画面は「Determine data structure（データ構造の判定）」という待ち受け状態になります。この状態のまま、次の手順に進みます。
5. ブラウザの別タブを開き、コピーした URL の末尾にパラメータを付けてアクセスします。

```
https://hook.○○.make.com/xxxxxxxx?name=山田&message=テスト送信です
```

6. ブラウザに `Accepted` と表示され、Make 側の待ち受けが「Successfully determined（判定に成功）」に変わればデータ構造の登録は完了です。
7. 2つ目のモジュールとして Gmail の「Send an Email」を追加し、本文やタイトルの入力欄で、Webhook から渡された `name` `message` の変数を選んで差し込みます。
8. 「Run once」でシナリオを起動し、待ち受け状態にしてから再度 URL にアクセスすると、メールが飛んできます。

## つまずいた点と解決

### 1. 待ち受けのタイミングを間違えて、データが登録されない

最初、URL を発行してからブラウザでアクセスするまでの順番を取り違えました。Make の画面を閉じたり、待ち受けが終了した状態で URL を叩いても、当然ながらデータ構造は登録されません。

**Make の Webhook は「待ち受け状態のときに届いたデータ」を見て、受け取る項目（データ構造）を自動で学習します。** ここを理解していなかったのが原因でした。

解決策はシンプルで、**必ず Make 側を「Determine data structure」の待ち受け状態にしてから、別タブで URL にアクセスする**という順番を守ることです。人間側の都合ではなく、Make 側が耳を澄ませている間に喋りかける、という感覚です。

この順番は、シナリオをテストする「Run once」でも同じです。Run once を押して待ち受け状態にしてから、URL を叩く。逆順だと何も起きません。

### 2. `?name=` を付け忘れて、受け取る項目が空になる

これが一番ハマりました。最初、発行された URL をそのままブラウザに貼り付けてアクセスしました。`Accepted` とは表示されます。しかし Make 側には**何の項目も登録されません**。

理由は、パラメータが付いていない URL には「渡す中身」が何も入っていないからです。Make は届いたデータを見て項目名を学習するので、中身が空なら学習するものがありません。

解決策は、URL の末尾に `?` を付けて `キー=値` の形式でデータを乗せることです。

- 1つ目のパラメータの前は `?`
- 2つ目以降の区切りは `&`

```
?name=山田&message=テスト送信です
```

この形で送ると、Make 側に `name` と `message` という2つの項目が認識され、Gmail モジュールの入力欄でそれらを変数として選べるようになります。

注意点として、**最初に送ったデータの形が、そのシナリオの「型」になります**。後から `company` という項目を追加したくなった場合は、Webhook の設定から「Re-determine data structure」を実行して、新しい形のデータをもう一度送り直す必要があります。最初のテスト送信の時点で、本番で使いたい項目をすべて含めておくのが結果的に早道でした。

### 3. 日本語を入れたときの文字化け

`?name=山田` のように日本語をそのまま URL に入れると、環境によっては文字化けします。ブラウザのアドレスバーから送る分には多くの場合そのまま通りますが、確実にやるなら URL エンコード（日本語を `%E5%B1%B1...` のような形式に変換すること）を通すか、テスト段階では英数字で `?name=test` として検証するのが安全でした。

## この学びが解決する実務の課題

Webhook が使えるようになると、「起きた瞬間に動く仕組み」が作れます。現場で価値が出そうなのは、次のような場面です。

- **問い合わせフォームの受信通知**：フォーム送信と同時に担当者へメール。15分おきのポーリングだと、初動が15分遅れます。
- **異常・不具合の報告**：現場から報告が上がった瞬間に関係者へ展開。
- **他システムからの連携**：自社の基幹システムや別のツールから「この処理が終わった」という合図を送り、後続作業を自動で回す。

つまり、**人が気づくまでのタイムラグを消せる**のが最大の価値です。現場の改善活動でいう「異常の即時検知」を、事務作業側でも実現できるようになります。

## 明日から使えるチェックリスト

Make で Custom webhook を設定するときに、この順番で確認してください。

- [ ] シナリオの**先頭**に Custom webhook を置いたか（途中には置けません）
- [ ] 発行された URL をコピーして控えたか
- [ ] **Make 側を待ち受け状態にしてから**、別タブで URL にアクセスしたか（順番厳守）
- [ ] URL に `?キー=値` のパラメータを付けたか（付けないと項目が登録されません）
- [ ] 2つ目以降のパラメータは `&` でつないだか
- [ ] **本番で使いたい項目をすべて**テスト送信に含めたか（後から追加すると再設定が必要）
- [ ] テスト段階のパラメータ値は英数字にしたか（日本語は文字化けの確認を）
- [ ] スケジュール設定が「Immediately as data arrives」になっているか
- [ ] 発行された URL は**誰でも叩ける**ので、社外に貼り付けていないか

## まとめ

Webhook は「見回り」から「呼び出しボタン」への転換で、待ち時間と無駄な実行回数の両方を削れます。
つまずいたのは、待ち受けの順番と `?name=` の付け忘れという、理屈を知っていれば防げる2点でした。
まずは自分宛てのメール送信という一番小さい形で、URL を1回叩くところから試すのが確実です。
